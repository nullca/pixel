# Midway Quest API — KID login + server-authoritative economy

Backend for the Midway Quest game (KPlay module). Go Fiber + PostgreSQL + Redis.

The goal is simple: **the client never decides how many coins, tokens or items a player has.**
The browser only reports *what happened* ("I finished a run in 72 s", "I picked answer 2").
The server checks it against rules, caps and the clock, then writes the result to an append-only ledger.

---

## 1. Why this is needed

Today every number lives in the player's browser (`localStorage` + artifact DB). Anyone can open DevTools and type
`S.coins = 999999`. That is fine for a prototype, but not once team rankings, the team fund or real prizes depend on it.

| Threat | Today | With this API |
|---|---|---|
| Edit coins / KP in DevTools | trivially possible | balance is read-only on the client, server owns it |
| Replay the same reward request | n/a | idempotency key per action, duplicate = no-op |
| Farm a minigame forever | partly capped in client | daily caps enforced in Postgres, per player per day (Asia/Bangkok) |
| Fake a perfect run / huge kite score | possible | session must exist, elapsed time must be plausible, reward is bounded |
| Pick a rare fish | possible | server rolls the fish with its own RNG |
| Look up quiz answers in JS | possible | client never receives the correct index; server grades |
| Impersonate another employee | n/a | identity comes only from a verified KID token |

> Honest limit: a determined player can still *play perfectly* through automation. We do not try to stop that.
> We make it **not worth it**: every coin source has a daily cap, so the most a cheater can earn per day is a
> known, small number, and suspicious patterns are flagged for admins.

## 2. Login flow (KID SSO)

```
Browser ──(1) open KPlay in Midway portal──▶ Portal (already logged in with KID)
Portal  ──(2) postMessage {access_token}───▶ Game iframe
Game    ──(3) Authorization: Bearer <JWT>──▶ Midway Quest API
API     ──(4) verify signature via KID JWKS, check iss/aud/exp
API     ──(5) upsert player (sub, name, dept, roles) and serve the request
```

* Token verification: `KID_JWKS_URL`, `KID_ISSUER`, `KID_AUDIENCE` (see `.env.example`).
* Claims used: `sub` (stable employee id), `name`, `department`, `roles` (contains `kplay-admin` for admins).
  Rename the claim keys in `internal/auth/kid.go` if KID uses different names.
* Department comes **from the token**, not from the client, so nobody can join another team's fund.

## 3. Data model (PostgreSQL)

* `players` — one row per employee (`id` = KID `sub`).
* `wallets` — current balance (`coins`, `kp`), `CHECK (coins >= 0 AND kp >= 0)`.
* `ledger` — **append-only** history of every change, with `UNIQUE (player_id, idem_key)`.
  Wallet = cached sum of ledger. If they ever disagree, the ledger wins.
* `daily_counters` — `(player_id, day, key) → count` for caps (`run`, `kite`, `balloon`, `sold:fish_nil`, …).
* `inventory` — `(player_id, item_id) → qty`, `CHECK (qty >= 0)`.
* `items` — catalogue with buy/sell prices and currency.
* `team_contrib` / `team_fund` — who gave what, and each department's total.
* `quiz_questions`, `quiz_attempts` — question bank lives on the server; attempts are the learning record for HR.
* `economy_config` — one JSON document of caps and rates, editable by admins (replaces the in-game settings panel).
* `anomalies` — flags raised by plausibility checks for admin review.

All money moves happen inside one transaction: lock wallet row → check caps → insert ledger → update wallet.

## 4. API (v1)

All routes need `Authorization: Bearer <KID token>`. Every **write** needs an `Idempotency-Key` header
(a UUID generated by the client per action). Sending the same key twice returns the first result.

### Player
| Method | Path | Purpose |
|---|---|---|
| GET | `/api/v1/me` | profile, wallet, inventory, today's counters, public config |

### Learning (strongest anti-cheat: answers never leave the server)
| Method | Path | Body | Result |
|---|---|---|---|
| POST | `/api/v1/quiz/next` | `{topic}` | `{token, prompt, choices}` (no answer) |
| POST | `/api/v1/quiz/answer` | `{token, choice}` | `{correct, explain, reward, wallet}` |

### Minigames (run, kite, fishing)
| Method | Path | Body | Result |
|---|---|---|---|
| POST | `/api/v1/minigame/start` | `{kind}` | `{session_id, started_at}` |
| POST | `/api/v1/minigame/finish` | `{session_id, result}` | `{reward, items, wallet, capped}` |

Rules (server side, see `internal/economy/rules.go`):
* session must exist, belong to the caller, and be used once (Redis, 15 min TTL);
* `run`: elapsed ≥ `run_min_seconds`, coins = `clamp(160 − seconds, 15, 145)`, only first `run_daily` per day;
* `kite`: score ≤ `kite_max_score_per_sec × elapsed`, coins = `min(80, score × 1.5)`, first `kite_daily` per day;
* `fish`: client only says "reeled in"; **server rolls the species and size**; capped by `fish_daily`.

### Collecting world items
| Method | Path | Body |
|---|---|---|
| POST | `/api/v1/collect` | `{kind}` → `shell`, `crystal`, `balloon`, `egg`, `hay`, `shake` … each with its own daily cap |

### Shop / sell / team fund
| Method | Path | Body |
|---|---|---|
| POST | `/api/v1/shop/buy` | `{item_id, qty}` |
| POST | `/api/v1/shop/sell` | `{item_id, qty}` → price decays after `sell_full` per item per day |
| POST | `/api/v1/team/contribute` | `{amount}` |
| GET | `/api/v1/team/:dept` | total, level, top contributors |

### Admin (role `kplay-admin`)
| Method | Path | Purpose |
|---|---|---|
| GET/PUT | `/api/v1/admin/config` | read / update caps and rates |
| POST | `/api/v1/admin/grant` | give or take coins/KP (audited in ledger with admin id) |
| GET | `/api/v1/admin/ledger?player=` | full history of one player |
| GET | `/api/v1/admin/anomalies` | flagged events |

## 5. Changes in the game client

`client/midway-api.js` is a small wrapper. The rule for the game code is:

* `S.coins`, `S.kp`, `S.inv` become a **display cache** filled from server responses.
* Every place that currently does `S.coins += x` or `addItem(...)` as a reward calls the API instead and
  renders whatever the server returns. Examples are in the file.
* Visual-only state (position, outfit, decoration layout, settings) can stay client-side.
* If the API is unreachable the game keeps working, but rewards are queued and shown as "รอยืนยัน"
  instead of being credited locally.

---

## 6. Rollout plan

1. Deploy API + DB next to the portal (`docker compose up`), wire KID JWKS.
2. Ship client in **shadow mode**: game still credits locally *and* calls the API; compare numbers for a week.
3. Switch the client to server-authoritative (local credits removed). Migrate each player's
   existing balance once via `admin/grant` with reason `migration`, capped to a sane maximum.
4. Remove the in-game economy settings panel; admins use `/admin/config`.
